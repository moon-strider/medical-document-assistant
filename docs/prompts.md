# Prompt and output contracts

The application has two inference roles, [answer](../prompts/roles/answer/AGENTS.md) and [judge](../prompts/roles/judge/AGENTS.md). Each has a short `base.md` instruction and a more detailed `AGENTS.md` policy. The Codex provider places the role's `AGENTS.md` in an isolated invocation directory and loads `base.md` through its configured role profile; the API provider sends both files as instructions. Both use the same application-built JSON task envelope and validate the result against their checked-in [answer](../prompts/schemas/answer.json) or [judge](../prompts/schemas/judge.json) schema. A schema that no longer matches its current Pydantic model fails rather than silently changing the contract.

The answer role emits either a structured answer or a bounded request for application-owned evidence tools. It has no direct tool authority. [`ModelAction`](../backend/src/medical_assistant/schemas.py#L85) records answer status, prose, cited claims, limitations, coverage requirement and at most two tool requests. The three available evidence operations are `search_evidence`, `read_evidence` and `collect_scope`; the graph decides when and how to execute them. **Dense baseline (V0)** uses fixed-chunk retrieval and the P0 payload: answer from citations, disclose retrieval limits and avoid unverified exhaustive or absence claims. **Hybrid + reranking + tool round (V3)** uses indexed hybrid retrieval and the P1 payload: it additionally stresses subject identity, event versus record time, medication order versus use, conflicts and complete citations for each material claim. P0 and P1 are [payload versions in the graph](../backend/src/medical_assistant/graph.py#L1150), not separate role files or output schemas. The dense baseline is final-only after its first evidence packet. The hybrid configuration can request one additional bounded [tool round](../backend/src/medical_assistant/graph.py#L1179), followed by a final-only answer call.

For a follow-up with history, or a question longer than the 512-character search limit, the same answer role first receives [`task_mode=query_planning`](../backend/src/medical_assistant/graph.py#L767) with empty evidence. It must return exactly one standalone `search_evidence` query or a `needs_clarification` answer; it cannot answer a clinical fact from prior conversation alone. The graph then retrieves fresh evidence and checks the final answer against the delivered packet, its receipt and the current collection revision. Source documents, quoted text and prior assistant turns are task data, not instructions; a document cannot grant tool access, alter the role or establish a clinical fact without source evidence.

The GPT 6 Sol High judge role uses a separate strict JSON schema and rubric. It receives the question, candidate answer, delivered excerpts, coverage receipt and frozen gold annotations through a [judge-only evaluation payload](../backend/src/medical_assistant/evaluation.py#L1821), and checks each material claim against its **own** citations before judging completeness, status and coverage. Gold is supplied only to this evaluation role, never to the answer generator or its query planner. For an evaluation campaign, the [judge rubric fingerprint](../backend/src/medical_assistant/providers/common.py#L105) hashes the exact judge `AGENTS.md` and `base.md` bytes. The campaign freezes and verifies that fingerprint with its code and configuration before producing results; changing the rubric cannot silently reuse the frozen campaign.
