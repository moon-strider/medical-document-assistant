# Trace delivery

`Telemetry(settings, store)` uses the application's PostgreSQL audit as the durable account of a run. `with telemetry.trace(run) as trace:` records `trace.planned` with a deterministic root `operation_id`, stores the original trace ID and pending status, then opens a Langfuse root observation with the same operation ID. `with telemetry.observation(name, kind, input, model=..., metadata=...)` adds child observations; an SDK failure returns a no-op observation and leaves the application run intact. The three evidence tools (`search_evidence`, `read_evidence`, `collect_scope`) and answer generations carry stable operation IDs at start and completion in audit and Langfuse metadata. A tool failure leaves its start open with an unknown result. Query planning uses `answer.plan_query`; answer generation uses `answer.generate`. `telemetry.score(run_id, name, value, ...)` first commits `trace.score_planned` to audit and then sends a deterministic score ID.

The root and recovered trace metadata carry only the compact frozen scope fields `id`, `collection_id`, `revision`, `source_count`, `ready_count`, `unavailable_count`, and `snapshot_hash`; source ID/hash inventories stay in PostgreSQL. Search observations expose bounded `retrieval` metadata with dense, BM25, literal and phrase candidate counts, RRF pool size, total search time, index scope, and per-stage embedding/dense/BM25/literal/phrase/fusion milliseconds. V3 also exposes reranker status, model and revision, input/scored/truncated-pair counts, and elapsed milliseconds. `search_observation_metadata(result)` whitelists these fields for both Langfuse search observations and run metrics; it does not copy candidate lists, snippets, or full chunk text into redundant metrics. The search tool's ordinary input/output remains available for individual private trace review. Each answer-generation observation separately preserves reported usage and hypothetical API-equivalent cost; retrieval instrumentation does not change those values.

`telemetry.reconcile_run(run_id)` confirms original successful-run delivery by matching every expected `(name, operation_id)` from audit to Langfuse v4 observations with distinct observation IDs, then checking planned scores. A completed SDK `flush()` or the number of similarly named spans alone does not prove delivery. Run status is `pending`, `original_materialized`, `recovered_from_audit`, `incomplete` or `unrecoverable`. A terminal run with malformed current operation IDs is `unrecoverable`; an incomplete but valid audit remains eligible for later checks. Late scores reset a materialized run to pending until the score appears in the read API. A successful run needs a complete audit before it can be exported as a separate `recovered_run` trace. A failed, cancelled, or interrupted run can instead be exported from its durable run status/error and the valid audit events that actually exist, including an open generation or tool with an unknown result. A queued terminal run can have zero known operations and no original trace. These terminal recovery records do not imply a complete original span tree, a provider result, usage, or an answer. Original observations for failed runs may exist, but the recovered record is the verified Langfuse representation of their terminal outcome. Recovery retains the original trace ID and timestamp provenance when present and marks `original_latency_measurement=false` and `original_tree_complete=false`. For an audit above 1 MiB it sends an explicitly compact summary with audit and answer hashes instead of the audit body. It uses one deterministic recovered trace ID per run and waits before a second emission if the first has not appeared. Repeated emissions can add observations to the same trace after a prolonged outage; exactly-once span replay is not claimed.

Run `uv run --project . python -m medical_assistant.telemetry_cli --once` for one eligible batch, or omit `--once` for a 30-second loop. Each pass selects at most 25 due terminal runs with `NULL`, `pending` or `incomplete` trace status; `--limit` can set 1–100. Terminal `NULL` runs are classified even when the Langfuse client is unavailable; pending/incomplete delivery waits for a configured client. The next attempt is calculated from durable `trace.reconcile_attempt` timestamps after the latest `trace.planned` or `trace.score_planned` event. The first pass is due after five seconds, later pending attempts wait 15 seconds with exponential backoff, and incomplete attempts start at 60 seconds; both cap at one hour. A late score resets the backoff. Incomplete traces remain eligible for later checks and can still materialize. `reconcile_run(run_id, force_recovery=True)` is available for a deliberate manual retry. Store methods own state changes; Langfuse is an optional view and never the denominator for experiment metrics. Private prompts, evidence, audit and scores are not sent to application SSE events or public exports. The trace root includes an `app_url` backlink to the run, while `runs.trace_url` points to the materialized Langfuse UI trace.

Evaluation reports fetch run status, model, usage, and minimal generation and billing audit facts in batches of at most 200 run IDs; the full audit remains available for individual review. The final comparison has 80 case attempts but can have more runs and provider calls because of two-turn questions, planning, and extra tool rounds. Judge calls and any later correction attempts remain in the evaluation ledger. Generation cost uses reported usage or the minimal audit facts when needed; unknown usage stays unknown rather than becoming a zero-cost call.

Generation observations keep the actual GPT 6 Sol or GPT 6 Luna model name so Langfuse shows an API-equivalent cost estimate. For Codex subscription calls, `billing_mode=subscription` and the actual amount billed for an individual call is unknown. `estimate_api_equivalent_cost(model, usage)` computes a separate reproducible estimate from CLI-reported tokens and `pricing_snapshot.json`. The snapshot records the 2026-09-25 Standard rates and sources: [GPT 6 Sol](https://developers.openai.com/api/docs/models/gpt-6-sol), [GPT 6 Luna](https://developers.openai.com/api/docs/models/gpt-6-luna), [pricing](https://developers.openai.com/api/docs/pricing), and [cache accounting](https://developers.openai.com/api/docs/guides/prompt-caching). The helper counts cached reads within total input once and never adds reasoning tokens to reported output again. Missing buckets or nonzero CLI cache-write tokens return an unknown estimate because this integration has not established the CLI cache-write partition semantics. The hypothetical estimate is never reported as a subscription charge.

Langfuse v4 [treats accepted observations as immutable](https://langfuse.com/faq/all/tracing-data-updates). Re-inserting an observation ID can duplicate rows and inflate metrics. Generation observations supply reported usage before the span ends; successful run roots include the published answer in their output.
